04 · SCREEN FLOW & TRANSITIONS

Make menus, gameplay and overlays cooperate as a stack.

The Screens module provides an abstract screen lifecycle and a ScreenManager component. It is intended for game flow: a menu over gameplay, a pause overlay, loading states, and replacement/close operations with optional visual transitions.

SCREEN LIFECYCLE

Override the hooks that match your resource and frame work.

A Screen is abstract: Update and Draw are required. The other hooks have empty defaults and are invoked by ScreenManager at the appropriate moments.

Hook / propertyWhen it is usedTypical responsibility
Initialize()The first time a manager shows the screen.Create non-content state and set initial screen configuration.
LoadContent()After initialization while the manager loads content.Load textures, maps, fonts or other screen resources.
OnActivated()Whenever the screen becomes the top screen.Resume input, reset selection or start an enter behaviour.
Update(GameTime&)When active, or when UpdateWhenInactive is true.Input, gameplay, timers and state changes.
Draw(const GameTime&)When active, or when DrawWhenInactive is true.Draw background, gameplay, UI or an overlay.
OnDeactivated()Whenever another screen becomes active.Pause, release capture or save a transient state.
UnloadContent() / Dispose()When the screen closes or its resources are released.Dispose screen-owned resources deliberately.

STACK SEMANTICS

Underlying screens are still present unless you remove them.

The manager stores screens bottom-to-top. The top screen is active, but underlying screens can continue rendering or updating if their properties request it.

Example: paused gameplay with an overlay

GameplayScreenbottom; draw while inactive
→
PauseScreentop; active and receives input
→
ScreenManagerupdates/draws allowed screens bottom-to-top

Stack operations

  • ShowScreen pushes a screen and makes it active.
  • CloseScreen disposes and removes the active screen, revealing the next one.
  • ReplaceScreen closes the active screen and shows another one.
  • ClearScreens disposes every tracked screen and leaves no active screen.

Non-owning screen pointers

  • The manager does not take ownership of the Screen* passed to it.
  • The caller retains the screen’s lifetime and can inspect it after CloseScreen has disposed it.
  • This is deliberately different from transition objects, which are handed in as std::unique_ptr.
!

Do not pass a temporary screen: ScreenManager records a non-owning pointer. Own the screen in your application or another stable object for as long as the manager might update, draw or close it.

TRANSITIONS

Move between states without inventing a second screen system.

Transitions are optional objects passed to show, close or replace operations. The manager owns them and drives their half-out/half-in state progression.

Transition

The abstract base exposes duration, state, value, state-changed and completed events, and the update/draw contract for a visual effect.

FadeTransition

A concrete fade effect that can be given to the manager through a std::unique_ptr.

ExpandTransition

A concrete expansion effect for another visual style of state change.

transition ownership
auto transition = std::make_unique<FadeTransition>(
  graphicsDevice, Color::Black, 0.35f);

screenManager.ReplaceScreen(&gameplayScreen,
  std::move(transition));

// ScreenManager owns the transition after this call.
// The caller still owns gameplayScreen.
i

Integration with World3DEXT: World3DScreenEXT inherits Screen. A 3D scene can therefore be shown, paused, replaced and transitioned by the ordinary ScreenManager alongside menus and 2D screens.
