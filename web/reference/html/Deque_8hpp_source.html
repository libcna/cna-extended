5// Ported from MonoGame.Extended's Collections/Deque.cs: a circular-array-backed double-ended
6// queue implementing sharp-runtime's System::Collections::Generic::IList<T> (matching how
7// sharp-runtime's own List<T> implements the same interface -- "reuse sharp-runtime, don't
8// re-roll"). C#'s `Func<int,int> ResizeFunction` maps to `std::function<intcs(intcs)>`, matching
9// this project's established Func<T> convention (HslColor.hpp's Match/Map).
10//
11// *** LIKELY UPSTREAM BUG, PRESERVED FOR FIDELITY -- the most significant one found in this
12// port so far, flagged prominently, not silently fixed ***
13// `IndexOf`'s final step computes `(index - _frontArrayIndex + _items.Length) % _items.Length`
14// from the raw `Array.IndexOf` result (`index`), WITHOUT checking whether that result was -1
15// (item not found in either physical segment). When the item genuinely isn't in the Deque, this
16// formula does NOT return -1 -- it computes some other, non-negative, seemingly-valid-looking
17// index instead. Traced by hand (see DequeTests.cpp's regression tests) and confirmed two
18// distinct, reachable failure modes:
19// 1. If the bogus computed index happens to fall within the "unused" tail of the backing
20// array (>= Count), `RemoveAt` on that index throws an unexpected exception.
21// 2. If the bogus computed index happens to fall within [0, Count) -- which depends entirely
22// on `_frontArrayIndex`'s current wraparound offset -- `Remove(item)` for a genuinely-absent
23// `item` SILENTLY REMOVES THE WRONG (unrelated, real) ELEMENT and reports success (`true`),
24// a real data-corruption risk for any code that calls `Remove` on items it isn't certain
25// are present.
26// This is preserved exactly (the "wrong index for a not-found item" formula is unchanged from
27// upstream) -- IndexOf/Remove genuinely can misbehave for absent items here, just like upstream.
28//
29// One further consequence is NOT preserved as pure UB, because it can't be: if the formula above
30// is evaluated on a *freshly-constructed, never-grown* Deque (`_items.Length == 0`, i.e. the
31// default `Deque()` constructor's `_emptyArray` sentinel, never resized by any Add/AddToFront/
32// AddToBack call), the modulo divisor is 0. In C#, integer `% 0` throws a *catchable*
33// `DivideByZeroException` -- meaning `new Deque<T>().Remove(anything)` genuinely crashes upstream
34// too, just via an exception rather than silently. In C++, integer modulo by zero is undefined
35// behavior, not a catchable exception -- there is no faithful way to preserve undefined behavior
36// as "the bug", since UB is not an observable, reproducible program behavior to preserve. This
37// port therefore explicitly detects exactly that one condition (empty backing array) and throws
38// `std::domain_error` instead, as the closest available C++ analog to C#'s catchable
39// `DivideByZeroException` -- everything else about the bug (wrong index, not -1, for a
40// genuinely-absent item once the Deque has any capacity at all) is left exactly as upstream.
41//
42// *** SECOND AND THIRD LIKELY UPSTREAM BUGS, PRESERVED FOR FIDELITY -- RemoveAt's middle-index
43// removal is unreliable outside a narrow case, confirmed EMPIRICALLY (not just by hand-tracing)
44// by running this port's own tests against it ***
45// `RemoveAt(index)` for an index strictly between the front and back has two branches
46// ("shift the shorter half" toward the removed slot, chosen by `index < Count / 2`). Both
47// branches pick their shift's *source* range from FIXED physical positions (`0` for the
48// front-half branch; `_items.Length / 2` for the back-half branch) rather than positions derived
49// from `_frontArrayIndex`, and both share the same `if (_frontArrayIndex < arrayIndex)
50// _frontArrayIndex = (_frontArrayIndex + 1) % _items.Length;` adjustment regardless of which
51// branch ran. Tracing (and then empirically confirming via this port's own test suite, since
52// this port is a faithful 1:1 translation of the algorithm) found:
53// - Front-half-shift branch on a NON-wrapped buffer (`_frontArrayIndex == 0`): CORRECT.
54// (`DequeTests.cpp`'s `RemoveAtMiddleShiftsShorterFrontHalf`.)
55// - Back-half-shift branch, even on the SAME non-wrapped buffer: BROKEN -- neither removes the
56// intended element nor preserves the order/values of the rest, because `arrayCenterIndex`
57// has no relationship to where the removal point or the front actually are.
58// (`RemoveAtMiddleShiftsShorterBackHalfReproducesKnownUpstreamBug`.)
59// - Front-half-shift branch once the buffer HAS wrapped (`_frontArrayIndex != 0`): ALSO
60// BROKEN -- an element can be silently lost/orphaned (its physical slot ends up outside the
61// new logical range after `_frontArrayIndex` is adjusted), replaced by a stale
62// default-constructed value. (`RemoveAtMiddleOnWrappedBufferReproducesKnownUpstreamBug`.)
63// In short: `RemoveAt` on a middle index is only confirmed reliable for a Deque that has never
64// wrapped AND happens to pick the front-half branch. This was not caught by upstream's own test
65// suite because its one relevant test (`Deque_Remove`) only asserts that `Count` decrements
66// correctly after each `RemoveAt` call, never that the *remaining values* are correct. All of
67// this is reproduced exactly (not fixed) below -- the C++ translation is algorithmically
68// identical to the C# source, verified line-by-line; this is upstream's behavior, not a
69// translation defect.
70//
71// Other, smaller preserved quirks:
72// - `CopyTo` validates `destinationIndex >= destination.size()` UNCONDITIONALLY, before the
73// `Count == 0` early-return check -- meaning `CopyTo(emptyDestination, 0)` throws even
74// though there is nothing to copy, rather than succeeding as a no-op. Preserved as-is.
75// - `IList<T>::Insert` always throws (upstream: `void IList<T>.Insert(...) =>
76// throw new NotImplementedException();`, an explicit-interface-implementation-only member --
77// Deque<T> only ever supports insertion at the front or back). Matches the precedent set by
78// `OrientedRectangle::setPositionProperty` (task 17: "matches upstream, always throws").
79//
80// Iteration: like sharp-runtime's own List<T>, this provides both the heap-allocated
81// IEnumerator<T>-based GetEnumerator() (to satisfy IEnumerable<T>/ICollection<T>/IList<T>) AND
82// plain STL-style begin()/end() for range-based `for` and direct test use.
83//
84// *** SUBTLE FIDELITY POINT: iteration is intentionally tolerant of concurrent front-removal ***
85// Upstream's `GetEnumerator()` is a C# iterator block (`yield return`); its `for` loop re-reads
86// `_frontArrayIndex`/`Count` LIVE on every loop-condition check, not just once when iteration
87// starts (only the loop *variable*'s initial value and the physical starting offset are captured
88// once). This is deliberate and upstream has a dedicated test for it
89// (`Deque_ForEach_Iteration_Modified`: repeatedly calling `RemoveFromFront()` from inside a
90// `foreach` over the same Deque, and expecting it to visit every remaining element exactly once
91// as the front shifts). A naive translation that snapshots `Count`/`frontArrayIndex_` once at
92// `begin()`, or that re-derives each element via the *logical* index through `operator[]` (which
93// itself reads the CURRENT, not the original, `frontArrayIndex_`), does not reproduce this.
94// Instead, `Iterator`/`Enumerator` capture the *physical* starting offset and capacity once (at
95// `begin()`/construction time), track a simple visited-count, compute each element's physical
96// index directly (`(originalFrontArrayIndex + visitedCount) % originalCapacity` -- verified by
97// hand to collapse upstream's two syntactically-different loop shapes, the non-wraparound single
98// loop and the wraparound two-loop, into one identical formula for the physical index actually
99// visited), and re-check LIVE `frontArrayIndex_ + count_` against `originalFrontArrayIndex +
100// visitedCount` for loop termination on every step -- reproducing upstream's live-bound behavior
101// exactly for the tested (front-removal-during-iteration) case.
102//
103// Header-only: a template, matching this project's established convention for generic C# types
104// (see Interval<T>, Triangulation/CyclicalList<T>).

233 [[nodiscard]] intcs IndexOf(const T& item) const override
234 {
235 T checkFrontBackItem;
236 if (Get(0, checkFrontBackItem) && checkFrontBackItem == item)
237 {
238 return 0;
239 }
240
241 const intcs backIndex = count_ - 1;
242 if (Get(backIndex, checkFrontBackItem) && checkFrontBackItem == item)
243 {
244 return backIndex;
245 }
246
247 const intcs capacity = static_cast<intcs>(items_.size());
248 intcs index;
249
250 if (count_ <= capacity - frontArrayIndex_)
251 {
252 index = ArrayIndexOf(item, frontArrayIndex_, count_);
253 }
254 else
255 {
256 index = ArrayIndexOf(item, frontArrayIndex_, capacity - frontArrayIndex_);
257 if (index < 0)
258 {
259 index = ArrayIndexOf(item, 0, frontArrayIndex_ + count_ - capacity);
260 }
261 }
262
263 if (capacity == 0)
264 {
265 // See this file's header comment: C#'s equivalent `% 0` throws a catchable
266 // DivideByZeroException here (a freshly-constructed, never-grown Deque); C++
267 // integer modulo by zero is undefined behavior instead, so this is explicitly
268 // guarded and thrown rather than left as UB.
269 throw std::domain_error("Deque<T>::IndexOf: division by zero (matches upstream's DivideByZeroException on an empty, never-grown Deque)");
270 }
271
272 // Matches upstream exactly: preserved as-is, including for `index == -1` (not
273 // found) -- see this file's header comment for the resulting bug.
274 return (index - frontArrayIndex_ + capacity) % capacity;
275 }

308 void RemoveAt(const intcs index) override
309 {
310 if (index < 0)
311 {
312 throw std::out_of_range("Index was less than zero.");
313 }
314 if (index >= count_)
315 {
316 throw std::out_of_range("Index was equal or greater than TotalCount.");
317 }
318
319 if (index == 0)
320 {
321 T discarded;
322 RemoveFromFront(discarded);
323 }
324 else if (index == count_ - 1)
325 {
326 T discarded;
327 RemoveFromBack(discarded);
328 }
329 else if (index < count_ / 2)
330 {
331 // See this file's header comment (SECOND/THIRD LIKELY UPSTREAM BUGS): this
332 // front-half-shift branch is only correct on a NON-wrapped buffer
333 // (frontArrayIndex_ == 0); once the buffer has wrapped, an element is silently
334 // lost/orphaned. Preserved exactly, not fixed.
335 const intcs arrayIndex = GetArrayIndex(index);
336 // Shift the array from 0 to before the index to remove by 1 to the right; the
337 // element to remove is overwritten by the copy.
338 ArrayCopy(items_, 0, items_, 1, arrayIndex);
339 items_[0] = T{};
340 if (frontArrayIndex_ < arrayIndex)
341 {
342 frontArrayIndex_ = (frontArrayIndex_ + 1) % static_cast<intcs>(items_.size());
343 }
344 count_--;
345 }
346 else
347 {
348 // See this file's header comment (SECOND LIKELY UPSTREAM BUG): this
349 // back-half-shift branch is broken even on a non-wrapped buffer -- its shift
350 // source, arrayCenterIndex, is a fixed physical midpoint with no relationship to
351 // the actual removal point, so it neither removes the intended element nor
352 // preserves the order/values of the rest. Preserved exactly, not fixed.
353 const intcs arrayIndex = GetArrayIndex(index);
354 const intcs arrayCenterIndex = static_cast<intcs>(items_.size()) / 2;
355 // Shift the array from the center to before the index to remove by 1 to the
356 // right; the element to remove is overwritten by the copy.
357 ArrayCopy(items_, arrayCenterIndex, items_, arrayCenterIndex + 1, static_cast<intcs>(items_.size()) - 1 - arrayIndex);
358 items_[items_.size() - 1] = T{};
359 if (frontArrayIndex_ < arrayIndex)
360 {
361 frontArrayIndex_ = (frontArrayIndex_ + 1) % static_cast<intcs>(items_.size());
362 }
363 count_--;
364 }
365 }

368 void Clear() override
369 {
370 if (count_ == 0)
371 {
372 return;
373 }
374
375 const intcs capacity = static_cast<intcs>(items_.size());
376 if (count_ > capacity - frontArrayIndex_)
377 {
378 std::fill_n(items_.begin() + frontArrayIndex_, capacity - frontArrayIndex_, T{});
379 std::fill_n(items_.begin(), frontArrayIndex_ + count_ - capacity, T{});
380 }
381 else
382 {
383 std::fill_n(items_.begin() + frontArrayIndex_, count_, T{});
384 }

386 frontArrayIndex_ = 0;

412 void CopyTo(std::vector<T>& destination, const intcs destinationIndex = 0) const
413 {
414 if (destinationIndex < 0)
415 {
416 throw std::invalid_argument("Index was less than the array's lower bound.");
417 }
418 if (destinationIndex >= static_cast<intcs>(destination.size()))
419 {
420 throw std::invalid_argument("Index was greater than the array's upper bound.");
421 }
422 if (static_cast<intcs>(destination.size()) - destinationIndex < count_)
423 {
424 throw std::invalid_argument("Destination array was not long enough.");
425 }
426
427 if (count_ == 0)
428 {
429 return;
430 }
431
432 const intcs capacity = static_cast<intcs>(items_.size());
433 const bool loopsAround = count_ > capacity - frontArrayIndex_;
434 if (!loopsAround)
435 {
436 std::copy_n(items_.begin() + frontArrayIndex_, count_, destination.begin() + destinationIndex);
437 }
438 else
439 {
440 const intcs firstSegmentCount = capacity - frontArrayIndex_;
441 std::copy_n(items_.begin() + frontArrayIndex_, firstSegmentCount, destination.begin() + destinationIndex);
442 const intcs secondSegmentCount = frontArrayIndex_ + (count_ - capacity);
443 std::copy_n(items_.begin(), secondSegmentCount, destination.begin() + destinationIndex + firstSegmentCount);
444 }
445 }

685 // Matches .NET's Array.Copy semantics: correctly handles overlapping in-place shifts
686 // (used by RemoveAt) regardless of shift direction, like memmove.
687 static void ArrayCopy(
688 std::vector<T>& source, const intcs sourceIndex, std::vector<T>& destination, const intcs destinationIndex, const intcs length)
689 {
690 if (length <= 0)
691 {
692 return;
693 }
694 if (&source == &destination && destinationIndex > sourceIndex && destinationIndex < sourceIndex + length)
695 {
696 std::copy_backward(source.begin() + sourceIndex, source.begin() + sourceIndex + length, destination.begin() + destinationIndex + length);
697 }
698 else
699 {
700 std::copy(source.begin() + sourceIndex, source.begin() + sourceIndex + length, destination.begin() + destinationIndex);
701 }
702 }
