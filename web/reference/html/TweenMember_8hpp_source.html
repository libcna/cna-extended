5// *** GENUINE C++ REDESIGN, NOT A LITERAL PORT -- approved by the user for this exact tradeoff ***
6// Replaces upstream's entire reflection-based member-access hierarchy: TweenMember.cs's abstract
7// `TweenMember`/`TweenMember<T>`, TweenFieldMember.cs's `TweenFieldMember<T>` (expression-tree-
8// compiled FieldInfo access), and TweenPropertyMember.cs's `TweenPropertyMember<T>` (expression-
9// tree-compiled PropertyInfo access). C++ has neither runtime reflection nor expression trees, so
10// a literal port is impossible; the C# lambda member-selector (`x => x.Position`) is replaced with
11// C++ pointer-to-member syntax (`&TargetType::Position`) -- syntactically similar at the call
12// site, fully compile-time type-checked, and needs no reflection machinery at all. This single
13// TweenMember<TTarget, TMember> class replaces the whole 4-class hierarchy: a C++ pointer-to-data-
14// member already works uniformly for what upstream needed two separate reflection paths
15// (FieldInfo vs PropertyInfo) to unify.
16//
17// LIMITATION, not present upstream: pointer-to-member syntax addresses public DATA MEMBERS
18// (fields) only. This project's own types often expose "C# properties" via getXProperty()/
19// setXProperty() method pairs instead of public fields (see CLAUDE.md's established convention).
20// Animating a getXProperty()/setXProperty() pair via this mechanism is out of scope -- only types
21// with an actual public field for the animated value are tweenable. Most simple animatable
22// values in this project (Vector2::X/Y, Color, float fields, etc.) are already public fields, so
23// this covers the common case; it does not cover types that only expose computed or validated
24// properties through accessor methods.
