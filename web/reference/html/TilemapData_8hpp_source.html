5// Ported from MonoGame.Extended's Tilemaps/TilemapData.cs: intermediate tilemap data produced by
6// format parsers (Tiled/LDtk/Ogmo, ported separately) and consumed by TilemapFactory to build the
7// real runtime object graph (Tilemap/TilemapLayer/TilemapTile/etc.). Upstream groups ~25 small
8// sealed/abstract classes into this one file via #region blocks; ported here as one header for
9// the same reason, matching the file-mirrors-namespace convention (all of them share the plain
10// root `MonoGame.Extended.Tilemaps` namespace).
11//
12// DESIGN DEVIATION, flagged for review: every type below uses plain public mutable fields
13// instead of this project's established `getXProperty()`/`setXProperty()` convention. These are
14// pure, behavior-free intermediate DTOs -- C# auto-implemented properties (`{ get; set; }`, no
15// validation or side effects) are semantically indistinguishable from plain fields here, and the
16// getXProperty() ceremony across ~150 total properties in ~25 types would add substantial bulk
17// with no behavioral benefit. This mirrors how `Size.hpp` (Phase 1) uses plain fields for a
18// C# type with genuinely plain fields -- the same reasoning is extended here to C#
19// auto-properties specifically because they carry no logic. This is a judgment call, not
20// silently made: flagged explicitly in this session's final report for the orchestrator to
21// confirm or override. If overridden, every type below would need the getXProperty()/
22// setXProperty() treatment instead.
23//
24// Ownership: `List<T> Properties`/`Tilesets`/`Frames`/`Tiles` (of *non-polymorphic* element
25// types like `TilemapPropertyData`, `TilemapTilesetEntry`, `TilemapAnimationFrameData`,
26// `TilemapDecodedTile`) are plain `std::vector<T>` (by value). `List<TilemapLayerData> Layers`
27// and `List<TilemapObjectData> CollisionObjects`/`Objects` (of *polymorphic, abstract-based*
28// element types) are `std::vector<std::unique_ptr<T>>` -- each entry is owned solely by the
29// list holding it, matching this project's established pattern for owning polymorphic
30// collections (e.g. `TilemapObjectLayer::objects_`). Nullable single references to a
31// non-polymorphic type (`TilemapTilesetEntry.InlineData`, `TilemapTileEntryData.Animation`) use
32// `std::optional<T>` rather than `std::unique_ptr<T>`, since nothing else aliases them and the
33// referenced type has no self-referential/forward-declaration need for pointer indirection.
