5// Ported from MonoGame.Extended's Math/Ray2.cs -- an OLDER, SEPARATE, minimal 2D ray type,
6// distinct from the richer, actively-used Ray2D.cs (already ported as Ray2D.hpp/.cpp). Both
7// types genuinely coexist in upstream, in the same MonoGame.Extended namespace, with different
8// names (`Ray2` here, `Ray2D` for the other): different field name (`Position` here vs
9// `Ray2D::Origin`), different feature surface (this type has exactly one method,
10// `Intersects(BoundingRectangle, out, out)`; `Ray2D` has a dozen `Intersects` overloads plus
11// GetPoint/ClosestPoint/Normalize/Deconstruct/CreateFromPoints). Confirmed via grep across both
12// upstream `source/` and `tests/`: this type has ZERO call sites anywhere in upstream itself
13// (only a one-line mention in a PrimitivesHelper.cs comment, "Used by Ray2 and Segment2") and no
14// test coverage -- it appears to be legacy/superseded by the Ray2D+Collision2D+Line2D/
15// LineSegment2D family, left in place rather than deleted. Ported anyway, at the project owner's
16// explicit request, for full fidelity even though it is dead code upstream.
17//
18// `IEquatableByRef<Ray2>` NOT implemented: matching the established precedent already set by
19// every sibling geometric value type in this project (BoundingBox2D, BoundingCircle2D,
20// BoundingCapsule2D, BoundingPolygon2D, OrientedBoundingBox2D, Line2D, LineSegment2D, Ray2D) --
21// none of them inherit `IEquatableByRef<T>` even where upstream implements it, since C++ value
22// types don't need runtime-polymorphic equality dispatch the way upstream's interface constraint
23// implies; a plain `Equals(const Ray2&) const` + `operator==` covers the same practical need.
24// C#'s `object obj` overload of `Equals` has no C++ equivalent (no universal object base) and is
25// not ported, matching `Line2D.hpp`'s identical precedent.
