5// Ported from MonoGame.Extended's Tilemaps/Rendering/TilemapWorldSpriteBatchRenderer.cs.
6// Unblocked for the same reason as its sibling TilemapSpriteBatchRenderer -- see that header's
7// comment; this renderer also draws exclusively through SpriteBatch::Draw.
8//
9// `IEnumerable<Tilemap> tilemaps` -> `const std::vector<Tilemap*>&` (non-owning: the renderer
10// never owns the tilemaps it bakes, matching TilemapSpriteBatchRenderer's `Tilemap*` convention).
11//
12// `Dictionary<WorldGroupKey, WorldGroup>`/`Dictionary<WorldRoomKey, WorldRoomBatch>` (both local
13// to `Load`, used purely for lookup-or-create grouping during the one-time bake pass) -> linear
14// `std::vector<std::pair<Key, Pointer>>` scans instead of a hash map, avoiding the need for a
15// `std::hash` specialization over a `Vector2`-containing key; load-time group/room counts are
16// small (bounded by distinct (depth, parallax[, tilemap]) combinations, not tile count), so O(n)
17// lookup here is not a real performance concern, unlike the per-tile Draw-time hot path.
18// `HashSet<TilemapTileData>` (dedup for `_animatedTiles`) -> `std::unordered_set<const
19// TilemapTileData*>`, which needs no custom hash (raw pointers hash natively).
20//
21// `List<WorldGroup> _worldGroups` / `WorldGroup.Rooms : List<WorldRoomBatch>` (both hold GC
22// references, kept stable as more items are added) -> `std::vector<std::unique_ptr<WorldGroup>>`/
23// `std::vector<std::unique_ptr<WorldRoomBatch>>`: `Load`'s local group/room index stores raw
24// pointers into these entries *while still adding more entries* (across the whole tilemap/layer
25// loop) -- a plain `std::vector<WorldGroup>` would invalidate those pointers on reallocation,
26// exactly the "reference stability across incremental appends" hazard already solved this way for
27// `TilemapLayerCollection`/`EntityManager` elsewhere in this project. `WorldRoomBatch.Tiles :
28// List<WorldTileSprite>` has no such aliasing concern (nothing holds a pointer into it across
29// appends), so it stays a plain `std::vector<WorldTileSprite>`.
30//
31// The three private nested types (`WorldGroupKey`/`WorldRoomKey`, `WorldTileSprite`,
32// `WorldRoomBatch`, `WorldGroup`) are declared entirely inside the .cpp (not this header) since
33// none of them appear in any public signature -- unlike `TilemapSpriteBatchRenderer`'s
34// `TileRenderPadding` (also private, but needed in the header because it's a private *member's*
35// type, so the class definition itself requires it complete). Here, `worldGroups_`'s element type
36// is `std::unique_ptr<WorldGroup>`, and a `unique_ptr`'s declaration only needs its pointee
37// forward-declared, not complete, so `WorldGroup` can be forward-declared here and defined only
38// in the .cpp, keeping this header's public surface uncluttered by definitions callers cannot see
39// or use.
