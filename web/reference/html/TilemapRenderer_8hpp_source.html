5// Ported from MonoGame.Extended's Tilemaps/Rendering/TilemapRenderer.cs.
6//
7// *** ARCHITECTURAL DEVIATION: DefaultEffect -> BasicEffect (not a literal port) ***
8// Upstream constructs its own `MonoGame.Extended.Graphics.Effects.DefaultEffect` (`_defaultEffect
9// = new DefaultEffect(_graphicsDevice) { TextureEnabled = true, VertexColorEnabled = true };`) and
10// draws through XNA's dynamic-reflection `Effect` API: `_effect.Parameters["Texture"].SetValue(...)`
11// then `foreach (EffectPass pass in _effect.CurrentTechnique.Passes) { pass.Apply(); ... }`.
12//
13// This project's own `DefaultEffect` (CNA::Extended::Graphics::Effects::DefaultEffect) was
14// deliberately hand-authored during Phase 5 with a GLSL vertex layout matching SpriteBatch's own
15// internal compact vertex format (`vec2 aPos`, `vec2 aTexCoord`, `vec4 aColor`) -- see that class's
16// own header comment. That layout is NOT compatible with XNA's standard `VertexPositionColorTexture`
17// (`Vector3 Position`, `Color`, `Vector2 TextureCoordinate`) that `TilemapRendererShared::
18// CreateLayerModel`/`AddTileQuad` (already ported, Phase 7) build vertex/index buffers for. Rather
19// than fork/extend `DefaultEffect` to add a second, incompatible vertex layout to a class that
20// already documents its SpriteBatch-only scoping as a known limitation, this port uses `cna`'s real
21// `Microsoft::Xna::Framework::Graphics::BasicEffect` instead:
22// - It is the genuine, standard XNA 4.0 effect class (`DefaultEffect` is MonoGame.Extended's own
23// invention, with no XNA equivalent).
24// - It is already fully implemented and pixel-verified across all 3 CNA backends (EasyGL/Vulkan/
25// Bgfx), specifically including `TextureEnabled=true` + `VertexColorEnabled=true` +
26// `LightingEnabled=false` over the exact `VertexPositionColorTexture` stride-24 vertex layout
27// this renderer uses -- see `cna/docs/basiceffect-support.md`.
28// - Its API (`World`/`View`/`Projection` public fields, `getTextureProperty()`/
29// `setTextureProperty()`, `getTextureEnabledProperty()`/`setTextureEnabledProperty()`, public
30// `VertexColorEnabled` field, `getLightingEnabledProperty()` defaulting to `false`) is a strict
31// superset of what `DefaultEffect` provided (`DefaultEffect` never had lighting at all).
32// The internal `defaultEffect_` member is configured with `TextureEnabled=true`,
33// `VertexColorEnabled=true` (leaving `LightingEnabled` at its default `false`) to reproduce
34// `DefaultEffect`'s always-on texture+vertex-color, no-lighting behavior exactly.
35//
36// A second, related deviation: upstream's public `Effect Effect { get; set; }` property accepts
37// ANY XNA `Effect` implementing `IEffectMatrices`, because the generic `Parameters["Texture"]`
38// indexer works against arbitrary user-defined effects via XNA's runtime parameter reflection.
39// CNA's `Effect` base class (see Effect.hpp's own doc comments) has NO such generic
40// Parameters/Techniques collection for built-in effects like `BasicEffect` -- there is nothing to
41// reflect into for a general "any effect" property. Since this renderer must set a concrete
42// texture on whatever effect is active, the public `Effect` property here is narrowed to
43// `BasicEffect&` specifically (still swappable -- a caller can substitute their own `BasicEffect`
44// instance, e.g. to install a different `RasterizerState`-adjacent configuration -- just not an
45// arbitrary unrelated `Effect` subclass). This mirrors `DefaultEffect.cpp`'s own precedent of
46// re-authoring the underlying apply mechanism in idiomatic C++ rather than translating a C#
47// mechanism (reflection-based `Parameters`/`CurrentTechnique.Passes`) that has no CNA equivalent.
48//
49// Draw mechanics: instead of the `Parameters["Texture"].SetValue(...)` / `foreach (EffectPass pass
50// in effect.CurrentTechnique.Passes) { pass.Apply(); ... }` walk, this port uses CNA's real, idiomatic
51// draw flow (see Effect.hpp/GraphicsDevice.hpp doc comments and BasicEffectTests.cpp /
52// rasterizerstate_cullmode_indexed_basiceffect_test.cpp for the established pattern this mirrors):
53// set effect properties (Texture, View/Projection/World) -> `GraphicsDevice::SetVertexBuffer` /
54// `SetIndexBuffer` -> `effect.Apply()` (which internally calls `GraphicsDevice::SetCurrentEffect`
55// and the effect's own `OnApply()`) -> `GraphicsDevice::DrawIndexedPrimitives(...)`. The backend
56// picks up the effect's state via `FillGpuDrawParams()` automatically; there is no
57// technique/pass collection to walk.
58//
59// `IDisposable`/`ThrowIfDisposed()` -> `System::IDisposable` + `System::ObjectDisposedException::
60// ThrowIf`, matching this project's established pattern for GPU-resource-owning types that need
61// deterministic release (see `CNA::Extended::Particles::ParticleEmitter`).
62//
63// `Dictionary<TilemapLayer, string>` (layer -> group name) -> `System::Collections::Generic::
64// Dictionary<TilemapLayer*, std::string>` (both key and value are copyable, matching this
65// project's established Dictionary<K,V> convention). `Dictionary<string, LayerGroup>`/
66// `Dictionary<TilemapTileLayer, List<LayerModel>>`/`Dictionary<TilemapImageLayer, LayerModel>`/
67// `Dictionary<TilemapImageLayer, RepeatImageLayerModel>`/`Dictionary<TilemapObjectLayer,
68// List<LayerModel>>` all have a move-only mapped type (`LayerGroup`/`LayerModel`/
69// `RepeatImageLayerModel` all own GPU `VertexBuffer`/`IndexBuffer` resources), which `System::
70// Collections::Generic::Dictionary`'s copy-based `TryGetValue`/indexer API cannot store -- plain
71// `std::unordered_map<K*, V>` is used directly for these instead, matching the identical, already-
72// established precedent in `TilemapTileset.hpp` (`std::unordered_map<int,
73// std::unique_ptr<TilemapTileData>> tileData_`, documented there in full) and
74// `TilemapWorldSpriteBatchRenderer.cpp`. `HashSet<string>` (`_drawnGroupsBuffer`/
75// `_groupsWithAnimations`) -> plain `std::unordered_set<std::string>`, matching
76// `TilemapWorldSpriteBatchRenderer.cpp`'s identical `HashSet<TilemapTileData>` ->
77// `std::unordered_set<const TilemapTileData*>` precedent (no custom hash needed for `std::string`
78// either).
79//
80// `LayerGroup`/`RepeatImageLayerModel` are private nested types (matching upstream's own private
81// nested classes) kept COMPLETE in this header (not just forward-declared, unlike
82// `TilemapWorldSpriteBatchRenderer.hpp`'s `WorldGroup`) because they are the mapped_type of member
83// fields (`layerGroups_`/`repeatImageLayerModels_`) declared in this class, which requires them
84// complete at this point -- same reasoning as `TilemapSpriteBatchRenderer.hpp`'s `TileRenderPadding`.
85// `RepeatImageLayerModel`'s fields are named in lowerCamelCase (`vertexBuffer`/`indexBuffer`/...)
86// rather than upstream's PascalCase (`VertexBuffer`/`IndexBuffer`/...): a field named `IndexBuffer`
87// of type `Microsoft::Xna::Framework::Graphics::IndexBuffer` (and similarly `Color` of type
88// `Color`) would shadow the type name for the remainder of the class body, a needless landmine for
89// a private, non-property-exposed struct with no C# get/set surface to mirror.
90//
91// The private nested `record TileBatch`/`readonly struct TileBatchKey`-shaped helper used inside
92// `BuildLayerModels(TilemapTileLayer&)`/`RebuildLayerGroupInternal`/`BuildMergedUngroupedModels` is
93// declared entirely inside the .cpp (not this header), since it is a local implementation detail of
94// those method bodies, never a member field's type -- matching
95// `TilemapWorldSpriteBatchRenderer.cpp`'s identical treatment of its own local grouping keys.
96//
97// `Tilemap tilemap` parameter of `LoadTilemap` -> `Tilemap*` (nullable, preserving upstream's
98// `ArgumentNullException.ThrowIfNull(tilemap)` check) rather than a dropped-null-check reference,
99// because `tilemap_` itself must be a nullable field (starts null, cleared by `UnloadTilemap()`) --
100// matching `TilemapSpriteBatchRenderer::LoadTilemap(Tilemap*)`'s identical precedent.
101// `OrthographicCamera camera` parameters elsewhere (`BeginDraw`/`Draw`/`DrawLayers`) -> `
102// OrthographicCamera&` with the null check dropped, since those are immediate-use non-null
103// parameters with no such nullable-field justification (matching `TilemapSpriteBatchRenderer`'s
104// identical `OrthographicCamera&` convention). `params string[] layerNames` -> `const
105// std::vector<std::string>&`, matching `TilemapSpriteBatchRenderer::DrawLayers`'s established
106// translation of the same C# construct.
107//
108// `LayerModel model` nullable parameter of `DrawLayerModel` -> `const LayerModel&` with the null
109// check dropped: every real call site passes an element from a `std::vector<LayerModel>`/
110// `std::unordered_map<K, LayerModel>` entry, never a null placeholder (C++ containers of `LayerModel`
111// by value cannot hold "null" elements the way a C# `List<LayerModel>` of nullable reference-type
112// elements formally could), so the defensive `model == null` guard has no reachable
113// C++ equivalent case.
114//
115// `model.Dispose()` walks in `UnloadTilemap()`/`RemoveLayerGroup()`/`RebuildLayerGroupInternal()` /
116// `BuildMergedUngroupedModels()` are NOT translated: `LayerModel`/`RepeatImageLayerModel` are plain
117// RAII types in this port (their owned `VertexBuffer`/`IndexBuffer` release their GPU handles in
118// their own destructors -- see `LayerModel.hpp`'s header comment), so clearing/erasing the
119// container that owns them is sufficient; there is nothing left to dispose manually.
120//
121// Upstream's real behavior (confirmed by reading every `Color` construction site in
122// `TilemapRenderer.cs`): only per-layer `Opacity` is baked into the vertex color alpha for tile,
123// image, and object layers -- `TilemapLayer.TintColor` is read nowhere in this class, unlike its
124// SpriteBatch-based sibling `TilemapSpriteBatchRenderer`, which does honor `TintColor`. This is
125// ported as-is (a genuine upstream inconsistency between the two renderers, not a bug this port
126// should silently "fix").
