5// Ported from MonoGame.Extended's Collections/ObservableCollection.cs and
6// Collections/IObservableCollection.cs: a Collection<T> that raises events on add/remove/clear.
7//
8// *** Distinct from sharp-runtime's own System::Collections::ObjectModel::ObservableCollection ***
9// plan.md originally chose to reuse sharp-runtime's real BCL ObservableCollection instead of
10// porting this MonoGame.Extended-specific one -- that decision still stands for general use.
11// This type is ported IN ADDITION, at the project owner's explicit request, for users who
12// specifically want MonoGame.Extended's own ObservableCollection/IObservableCollection surface
13// (four separate events -- ItemAdded/ItemRemoved/Clearing/Cleared -- rather than sharp-runtime's
14// single CollectionChanged event with a change-description payload). The two types are not
15// related and are not interchangeable; pick whichever event shape a given call site needs.
16//
17// `Collection<T>` (the C# base class, System.Collections.ObjectModel.Collection<T>) ->
18// sharp-runtime's own `System::Collections::ObjectModel::Collection<T>`, which already exposes
19// the exact same protected virtual hooks this type overrides (InsertItem/RemoveItem/ClearItems/
20// SetItem), per this project's "reuse sharp-runtime, don't re-roll" convention.
21//
22// `event EventHandler<ItemEventArgs<T>> ItemAdded/ItemRemoved` / `event EventHandler Clearing/
23// Cleared` -> public `System::EventHandler<...>` members + `getXEvent()` accessors, matching
24// `FramesPerSecondCounter.hpp`'s established pattern for exposing events on a type deriving
25// `System::Object`. `System::EventHandler<TEventArgs>::Raise` requires a `System::Object*`
26// sender (see EventHandler.hpp's own doc comment on why this C++ port bundles subscriber storage
27// into the handler type itself); `Collection<T>` alone has no `Object` in its inheritance chain,
28// so this type additionally inherits `System::Object` (no diamond: `Collection<T>`'s own base,
29// `Generic::IList<T>` -> `ICollection<T>` -> `Generic::IEnumerable<T>` -> `Collections::
30// IEnumerable`, never touches `Object`) purely to have a valid `this` to pass as sender.
31// `GetTypeName()` returns a fixed, non-templated string (`"MonoGame.Extended.Collections.
32// ObservableCollection"`) rather than attempting to embed `T`'s name -- matching this project's
33// established "reflection-hazard, use a fixed sensible string" precedent (see GameTimer's
34// constructor-supplied name), since C++ has no clean, demangling-free way to reproduce C#'s
35// `GetType().Name` for an arbitrary template instantiation, and upstream's own reflection-based
36// name (e.g. "ObservableCollection\`1[System.Int32]") isn't something meaningfully portable
37// anyway.
38//
39// `IList<T> list` constructor overload -> takes a `const std::vector<T>&` to seed initial items
40// (matching `Collection<T>`'s own `std::vector<T>`-backed storage; `Collection(IList<T>)`'s
41// upstream null-check has no C++ equivalent need since a `const std::vector<T>&` can't be null).
42//
43// Header-only: a template, matching this project's established convention for generic C# types
44// (see Interval<T>/KeyedCollection<TKey,TValue>).
