5// Ported from MonoGame.Extended's Input/InputListeners/MouseListener.cs. `Func<MouseState,
6// ButtonState>` private helper parameters -> `std::function<ButtonState(const MouseState&)>`.
7// `_mouseDownArgs`/`_previousClickArgs` (nullable MouseEventArgs fields) -> std::optional<MouseEventArgs>.
8//
9// *** POSSIBLE UPSTREAM EDGE-CASE BUG, PRESERVED FOR FIDELITY, NOT FIXED ***
10// CheckButtonReleased/CheckMouseDragged read `_mouseDownArgs.Button` (upstream) /
11// `mouseDownArgs_->getButtonProperty()` (here) WITHOUT checking it is non-null/has_value() first.
12// If a MouseUp or drag-motion frame occurs before any MouseDown was ever recorded for this
13// listener (e.g. the listener is attached to an already-held button, or Update() is first called
14// mid-press), upstream would throw NullReferenceException; this port has the same unchecked
15// access via std::optional::operator->, which is undefined behavior on an empty optional rather
16// than a clean exception -- ported as-is (not guarded), matching this project's "preserve found
17// issues, document them" convention, since fixing it would silently change upstream's error
18// behavior. In ordinary usage (CheckButtonPressed always runs before CheckButtonReleased/
19// CheckMouseDragged for the same button within one Update()), mouseDownArgs_ is always set by the
20// time these branches are reached, so this is a genuine but narrow edge case, not a
21// hot-path concern.
