5// Ported from MonoGame.Extended's OrthographicCamera.cs: a sealed Camera<Vector2> that also
6// implements IMovable/IRotatable. Deferred since Phase 1 (see plan.md's Phase 1 notes) pending
7// `ViewportAdapters`, which landed in Phase 3 -- ported now as a necessary prerequisite for
8// Phase 7's Tilemaps/Rendering/* module, all four of whose renderer classes require this type.
9//
10// Ownership: upstream's `_viewportAdapter` field is a plain GC-rooted reference -- when
11// constructed via `OrthographicCamera(GraphicsDevice)`, C# implicitly keeps the new
12// `DefaultViewportAdapter(graphicsDevice)` alive for as long as the camera references it, with no
13// other owner needed. `ViewportAdapter` (this project's port) takes its `GraphicsDevice&` non-owning,
14// by reference, matching the established "adapter never owns, always references an
15// externally-owned, longer-lived object" convention -- so `OrthographicCamera` mirrors that same
16// convention for its own `_viewportAdapter` field (`viewportAdapter_`, a `ViewportAdapter&`).
17// That leaves the `GraphicsDevice&`-only constructor with nothing to hold the
18// `DefaultViewportAdapter` it must create: `ownedViewportAdapter_` (new, no direct upstream field)
19// is the owner in that case only, mirroring `Tilemap::ownedTextures_`/`BitmapFont::pageTextures_`'s
20// identical C#-GC-vs-C++-value-return problem and solution. `viewportAdapter_` then references
21// either the caller-supplied external adapter, or `*ownedViewportAdapter_` -- declaration order
22// (below) matters here: `ownedViewportAdapter_` must be declared before `viewportAdapter_` so it's
23// initialized first regardless of member-initializer-list order.
24//
25// `sealed` -> `final`. Implements `Camera<Vector2>`, `IMovable`, `IRotatable` simultaneously --
26// `IMovable`/`IRotatable`'s `getPositionProperty`/`setPositionProperty`/`getRotationProperty`/
27// `setRotationProperty` have identical signatures to `Camera<Vector2>`'s own (not a coincidence:
28// upstream's `Camera<T>` doesn't itself implement these interfaces, but `OrthographicCamera`
29// implements all three side by side) -- since the three base classes are unrelated (no shared
30// ancestor, so no diamond), a single override in this class satisfies all matching pure virtuals
31// from all three bases at once; standard, well-defined C++ behavior.
32//
33// Copy/move: deleted. `viewportAdapter_` is a reference member (can't be reseated on
34// assignment), and this is a top-level, once-constructed-and-kept game object in upstream too
35// (`sealed`, no upstream code ever copies or reassigns one) -- matching this project's
36// `SpriteBatch`-style "construct once, reference thereafter" convention rather than adding
37// move support upstream never needed.
