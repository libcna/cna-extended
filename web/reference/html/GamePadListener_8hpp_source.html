5// Ported from MonoGame.Extended's Input/InputListeners/GamePadListener.cs. `Enum.GetValues(typeof(Buttons))`
6// has no C++ reflection equivalent -- ported as a static const std::array<Buttons, 31> literal in
7// the .cpp, listing every Buttons enumerator CNA defines (including its FNA-extension values
8// Misc1EXT/Paddle1-4EXT/TouchPadEXT, which upstream's real XNA Buttons enum does not have -- a
9// genuine, unavoidable set-size difference between the two languages' Buttons enums, not a
10// fidelity gap in the port itself), ordered by ascending numeric flag value to match .NET's
11// observed Enum.GetValues ordering for flags enums.
12//
13// *** SUSPICIOUS CONTROL FLOW FOUND, INVESTIGATED, PRESERVED AS-IS (empirically harmless here) ***
14// Upstream's CheckAllButtons() does `if (_excludedButtons.Contains(button)) break;` inside the
15// all-buttons loop -- `break`, not `continue`. A `break` here would, in general, wrongly abort
16// the whole loop on the FIRST excluded button rather than skipping just that one. Investigated by
17// checking the actual numeric ordering of every Buttons value: all 10 excluded buttons
18// (LeftTrigger/RightTrigger/*ThumbstickUp/Down/Left/Right) happen to be exactly the buttons with
19// the highest flag bits, clustered contiguously at the end of ascending-numeric order, with no
20// non-excluded button positioned after them. So breaking on the first excluded button reached
21// (in ascending order) never actually skips a legitimate button -- everything remaining past that
22// point is excluded anyway. Ported as `break` (not silently "fixed" to `continue`), since fixing
23// it would diverge from upstream even though the observable behavior happens to be identical
24// either way for this specific enum layout; if CNA's Buttons enum values are ever renumbered,
25// this coincidence would stop holding and the bug would start to matter.
