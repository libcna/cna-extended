4// CNA::Extended::World3DEXT::Text3DEXT -- new, non-upstream addition. See 3d.md/plan3d.md
5// at the repository root for the design.
6//
7// 3D counterpart of BitmapFontExtensions::DrawString: floating, world-space text labels,
8// rendered as a small number of camera-facing billboard meshes (one per distinct font page
9// texture the string's glyphs use) instead of a 2D SpriteBatch.DrawString call. Reuses this
10// project's already-ported BitmapFonts::BitmapFont glyph layout (BitmapFont::GetGlyphs --
11// real kerning/line-layout logic, not re-implemented here) -- BuildText3DMeshEXT only
12// converts BitmapFont's already-laid-out 2D pixel-space glyph quads into 3D local-space
13// mesh parts (Y flipped: BitmapFont's layout is Y-down screen space, this mesh is Y-up so
14// upright text reads correctly once billboarded).
15//
16// Multi-page support (Phase 12 D, 2026-07-15, user-requested "extend later" item): originally
17// this assumed every glyph in a string came from the same font page texture (true for any
18// single-page BMFont, the overwhelmingly common case), silently skipping glyphs from a
19// second page rather than starting a second draw batch. Text3DEXT/Text3DMeshEXT now hold a
20// vector of per-page parts instead of one flat mesh -- BuildText3DMeshEXT groups glyphs by
21// their page texture (preserving first-seen page order) into one Text3DMeshPartEXT per
22// distinct texture, and TextBillboardRenderSystemEXT issues one draw call per part (texture
23// swap between parts, same per-part draw-call shape the single-mesh version always had --
24// this is "repeat the existing single-texture draw once per page", not a new drawing
25// strategy). The 2D BitmapFontExtensions::DrawString equivalent has no comparable multi-page
26// grouping logic to mirror -- it draws one glyph at a time and lets SpriteBatch's own
27// per-texture batching handle page grouping implicitly, which doesn't apply to this combined
28// single/multi-VertexBuffer 3D mesh design.
