5// Ported from MonoGame.Extended's Collisions/CollisionWorld2D.cs: the primary query-oriented
6// actor/world collision API, storing actors in named layers and coordinating broadphase,
7// narrowphase, and pair-query operations across them. Completes Phase 2 task 2, deferred since
8// entry (25) pending Layer/LayerPair (task 4) and the broadphase implementations (task 3), both
9// now landed.
10//
11// Ownership: `Dictionary<string, Layer> _layers` -> `std::unordered_map<std::string,
12// std::unique_ptr<Layer>>` (CollisionWorld2D owns every Layer it's given, matching upstream's own
13// intent -- a Layer is constructed specifically to be handed to a CollisionWorld2D and nothing
14// else ever holds a second reference to it). `Dictionary<ICollisionActor, string>
15// _actorLayerNames` -> `std::unordered_map<ICollisionActor*, std::string>` (non-owning actor
16// pointers, matching this whole module's established ICollisionActor* convention).
17// `HashSet<LayerPair> _layerCollision` -> `std::unordered_set<LayerPair>`.
18//
19// C#'s `null` layerName parameters (meaning "use the default layer", resolved by GetLayer's
20// `layerName ?? DefaultLayerName`) have no direct std::string equivalent. Translated using an
21// empty string as the "not specified" sentinel throughout (default argument `= ""` where upstream
22// defaults to `null`, or an always-required-but-null-tolerant `const std::string&` parameter
23// elsewhere) -- GetLayer resolves an empty layerName to DefaultLayerName, mirroring upstream's
24// null-coalescing exactly. This is deliberately narrower than std::string::empty() might suggest:
25// only GetLayer treats "" specially; methods that validate their layerName argument BEFORE calling
26// GetLayer (Insert, MoveToLayer) still reject "" outright via
27// System::ArgumentException::ThrowIfNullOrWhiteSpace, exactly matching upstream's own
28// ArgumentException.ThrowIfNullOrWhiteSpace(layerName) calls in those methods -- so "" never
29// actually reaches GetLayer's resolution logic from Insert/MoveToLayer, only from the methods that
30// truly allow an omitted/unspecified layer name (QueryCandidates, QueryCollisions,
31// QueryCollisionPairs, EnableCollisionBetweenLayers/DisableCollisionBetweenLayers/
32// IsCollisionEnabledBetweenLayers). One deliberately-accepted, narrow fidelity gap: upstream's
33// `??` only coalesces true C# null, not an explicitly-passed empty string -- so
34// `QueryCandidates(bounds, "")` in real C# would look up a literal ""-named layer and throw
35// UndefinedLayerException, whereas this port resolves it to the default layer. No legitimate use
36// case can hit this (AddLayer/RemoveLayer already reject "" as a layer name outright, so a
37// ""-named layer can never exist to be found either way), and upstream's own test suite never
38// exercises it.
39//
40// `IEnumerable<ICollisionActor>`/`IEnumerable<CollisionEvent2D>`/`IEnumerable<CollisionPair2D>`
41// return types (including two upstream `yield return` generators, QueryCollisions and
42// QueryCollisionPairs) -> eagerly-built `std::vector<T>`, matching the convention already
43// established in ICollisionBroadphase2D.hpp for this whole module.
44//
45// `System.Data.DuplicateNameException` (thrown by AddLayer on a duplicate name) has no
46// sharp-runtime equivalent -- checked and confirmed missing, not assumed; sharp-runtime is a
47// sibling repository this project does not modify. Substituted with
48// `System::ArgumentException`, matching real .NET BCL precedent for duplicate-key scenarios
49// (Dictionary<TKey,TValue>.Add itself throws ArgumentException for a duplicate key), and
50// documented here as a deliberate substitution, not a silent scope decision.
