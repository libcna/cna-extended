13// Two deliberate, purely-mechanical simplifications with no observable behavioral consequence:
14// - Upstream's `_isPrimitive` (`typeof(T).IsPrimitive`) exists solely to skip `Array.Clear` for
15// primitive T as a garbage-collector hygiene hint -- C++ has no GC to hint, so this always
16// clears emptied/removed slots to `T{}` unconditionally instead. `Count` bookkeeping is
17// identical either way; nothing about the public API's observable behavior changes.
18// - Upstream's `BagEnumerator` struct plus the `IEnumerable<T>.GetEnumerator()`/
19// `IEnumerable.GetEnumerator()` triad exist solely so C#'s `foreach` can avoid
20// heap-allocating/boxing an enumerator -- a struct-vs-interface distinction with no C++
21// analog (range-based `for` over `begin()/end()` never allocates regardless). Replaced with
22// plain `begin()`/`end()` (mutable and const) iterating the backing array's first `Count`
23// elements directly.
24//
25// Upstream's `this[int index]` is a single C# indexed property with asymmetric get/set behavior
26// (get returns `default(T)` for an out-of-range index without growing; set auto-grows the Bag).
27// C++'s `operator[]` cannot express two different behaviors for read vs. write through the same
28// syntax without returning a reference from both (which the get side can't safely do for an
29// out-of-range index, since there is no live T to reference). Split into a read-only
30// `operator[](index) const` returning by value (matching the get side exactly, including
31// returning `T{}` rather than growing/throwing) and a separate `Set(index, value)` method
32// (matching the set side exactly, including auto-growing).
33//
34// Header-only: a template, matching this project's established convention for generic C# types
35// (see Interval<T>, Triangulation/CyclicalList<T>).
