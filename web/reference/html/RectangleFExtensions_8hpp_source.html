8// *** LIKELY UPSTREAM BUG, PRESERVED FOR FIDELITY -- flagged prominently, not silently fixed ***
9// Clip(rectangle, clippingRectangle) does NOT compute a true geometric intersection (unlike
10// RectangleExtensions::Clip, the analogous method for the integer Rectangle type, which uses
11// proper min/max intersection logic). Instead it mutates X/Y first, then derives Width/Height
12// from the Right/Bottom properties computed off the *already-mutated* X/Y -- not the original
13// rectangle's bounds. Concretely verified (see Clip's implementation comment and
14// RectangleFExtensionsTests.cpp's regression tests for hand-traced examples): when only the
15// left/top edge needs clipping and the right/bottom edge does not, Width/Height are left
16// unchanged instead of shrinking to account for the moved left/top edge, producing a rectangle
17// larger than the true intersection. When the clip rectangle doesn't overlap the source at all,
18// Clip does not detect this and does not return RectangleF::Empty -- it silently produces a
19// bogus non-empty "intersection" positioned at the clip rectangle's own X/Y. This is upstream's
20// actual behavior, reproduced exactly below rather than "fixed" to be geometrically correct.
