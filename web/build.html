CMAKE SURFACE

Know which option decides which part of the build.

The project is CMake 3.20+ and sets C++23 as a required, non-extension language mode.

THREE CONFIGURATION MODES

Use the mode that matches your integration.

There is no ambiguity in target discovery: CMake selects one of these paths in a defined order.

01

Parent target

Your game’s parent CMake build has already defined CNA. cna-extended links that target automatically and inherits its backend choice.

02

Standalone linked

LINK_CNA=ON causes cna to be added from CNA_EXTENDED_CNA_DIR. This is the normal way to build examples and run graphics tests from the repository.

03

Headers-only fallback

With no parent target and LINK_CNA=OFF, public cna/sharp-runtime headers are included for compile checking. It is not a fully linked runtime configuration.

HEADLESS RENDERING

Graphics tests still need a real video path.

The linked configuration creates a genuine GraphicsDevice. A test that reads pixels from a render target is not a pure CPU test even if it has no visible application window.

Verified environments

A real X11/Wayland session with DISPLAY works normally. A truly headless invocation can use DISPLAY= xvfb-run -a <binary> with a Mesa software renderer such as llvmpipe.

When a sandbox fails

An error such as SDL video initialization failing signals a missing usable video driver/server path, not a failed cna-extended assertion. Check Xvfb and Mesa DRI software-renderer availability.

RENDER READBACK GOTCHAS

Use cna’s documented workaround for offscreen pixels.

These are recorded cna API-shape differences discovered while testing cna-extended. They are not defects in the cna-extended map renderers.

Do not use Texture2D::GetData for rendered RT pixels

In the current cna implementation it reflects the CPU-side data set by SetData, not GPU rendering into a RenderTarget2D. Read the currently bound framebuffer through GraphicsDevice::GetBackBufferData before unbinding instead.

Pass an explicit rectangle

The no-rectangle GetBackBufferData overload uses viewport dimensions rather than the currently bound render target size. For offscreen targets, pass a Rectangle matching the target’s width and height.

safe cna render-target readback
graphicsDevice.SetRenderTarget(&renderTarget);
// ... issue draw calls while this framebuffer is bound ...

Rectangle region(0, 0,
  renderTarget.getWidthProperty(),
  renderTarget.getHeightProperty());
graphicsDevice.GetBackBufferData(
  &region, pixels.data(), 0, static_cast<int>(pixels.size()));

graphicsDevice.SetRenderTarget(nullptr);
