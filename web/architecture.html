C++ TRANSLATION RULES

Important conventions before you write gameplay code.

They are consistent across the port, so learning them once avoids many otherwise surprising ownership and naming mistakes.

01

Namespace and file layout

Public types live under CNA::Extended and module subnamespaces such as Tilemaps, Particles or ECS. A header’s path mirrors its namespace.

02

Property translation

Read a C# property with getXProperty() and change it with setXProperty(). This avoids ambiguous C++ field exposure while retaining the original API’s intent.

03

Ownership is part of the API

std::unique_ptr represents transfer of ownership. Raw pointers commonly identify non-owning game objects or components that must outlive the library reference.

04

References mean non-null

Many APIs use references where the C# counterpart accepted a non-null object. Do not pass a temporary object when the library stores it for later use.

05

Vector-like results are eager

Several C# enumerable or yield APIs become concrete std::vector results. Treat a query result as a snapshot rather than a lazy stream.

06

Runtime formats over pipelines

Design-time MGCB and XNB readers are outside the scope. Direct Tiled, LDtk, Ogmo, TexturePacker, BMFont and XML/JSON paths are the intended workflow.

LIFECYCLES

Choose the object that should own the loop.

Screen flow, ECS and World3DEXT are complementary. The right choice depends on the scope of state you need to manage.

Screens::ScreenManager

Use a stack of screens for menus, loading states, pause layers, transitions, or distinct gameplay modes. Each screen uses the familiar initialize, content, update and draw lifecycle.

ECS::World

Use a World whenever many entities share component-shaped state and system-shaped behaviour. The World owns registered systems and coordinates update/draw passes.

World3DScreenEXT

Use the convenience base when a screen itself is a 3D scene. It owns one ECS World and one Camera3DEXT while retaining the ordinary Screen lifecycle.

ownership in an ECS world
ECS::WorldBuilder builder;
builder.AddSystem(std::make_unique<MovementSystem>());

std::unique_ptr<ECS::World> world = builder.Build();
ECS::Entity& entity = world->CreateEntity();

Position position{};
entity.Attach(&position);

// The caller owns position; it must outlive the attachment.
world->Update(gameTime);
!

Lifetime matters: a component attached through Entity::Attach is not copied into the World. Keep the component storage alive until it is detached or its entity is destroyed.

WHAT IS DELIBERATELY NOT HERE

Understand the boundaries before planning a pipeline.

Scope exclusions are design choices, not missing accidental documentation.

Excluded

  • MonoGame.Extended.Content.Pipeline and MGCB-oriented design-time tooling.
  • Runtime readers whose only job is consuming XNB output from that pipeline.
  • A second parallel Scene/SceneManager abstraction for 3D.

Use instead

  • Direct-format data loaders and a normal filesystem/content workflow.
  • ScreenManager for screen transitions and flow.
  • World3DScreenEXT for a 3D scene with Screen semantics.
