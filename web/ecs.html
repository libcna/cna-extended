09 · ENTITY COMPONENT SYSTEM

Let data and systems shape the gameplay loop.

The ECS module is an Artemis-style entity-component system. Entities are lightweight IDs, components are your data, and systems operate on matching entities through aspects and component mappers.

Build a world ↓Use ECS in World3DEXT

ECS::WorldBuilder builder;
builder.AddSystem(std::make_unique<MovementSystem>());

auto world = builder.Build();
ECS::Entity& hero = world->CreateEntity();
hero.Attach(&position);
hero.Attach(&velocity);

world->Update(gameTime);
World owns systems; your game controls component lifetimes

CORE MODEL

World, entity, component, system.

Each piece is small by design. The composition happens in your WorldBuilder and in the component types your game defines.

WorldBuilder

Add std::unique_ptr<ISystem> in the order you want to register them. Build() returns a std::unique_ptr<World>.

World

Creates entities, owns the entity/component managers and drives registered systems through update/draw calls.

Entity

A cheap handle with a stable integer ID. It attaches, gets, tests and detaches components through the World’s storage.

ComponentManager

Coordinates component storage by type; ComponentMapper provides the typed access path for each component type.

Aspect

Describes the component combination a system is interested in. AspectBuilder helps construct that filter.

EntitySubscription

Tracks entities that currently match a system’s aspect so systems do not scan arbitrary game objects manually.

SYSTEMS

Use the base class that matches your frame responsibility.

The system classes express whether your work happens once per frame or once per matching entity, and whether it belongs to Update or Draw.

TypeUse it whenTypical work
UpdateSystemOne update operation per World frame.Global timers, scene-wide state, command queues.
DrawSystemOne draw operation per World frame.Camera-wide render setup or composed passes.
EntityUpdateSystemUpdate matching entities individually.Movement, AI, health regeneration, particle simulation.
EntityDrawSystemDraw matching entities individually.Sprites, models, billboards, debug visualisation.
EntityProcessingSystemYou need a customised per-entity processing shape.More specialised entity lifecycle logic.

COMPONENT LIFETIMES

Attach pointers deliberately.

The port preserves a C++ distinction that a managed C# ECS does not need to expose: attaching a component does not mean the World starts owning it.

a minimal component and entity
struct Position { float X = 0.0f; float Y = 0.0f; };
struct Velocity { float X = 0.0f; float Y = 0.0f; };

Position position{32.0f, 48.0f};
Velocity velocity{16.0f, 0.0f};

ECS::Entity& entity = world->CreateEntity();
entity.Attach(&position);
entity.Attach(&velocity);

if (entity.Has<Velocity>())
  entity.Get<Velocity>()->X = 0.0f;

entity.Detach<Velocity>();
entity.Destroy();  // queues entity destruction through EntityManager
!

Store components somewhere stable: a stack component is fine only if the World does not outlive the enclosing scope. For long-lived entities, store components in an owning game object, a stable container, or another explicit allocation strategy.

WHERE ECS FITS

Use it for repeated entity logic, not every object by default.

ECS becomes more valuable as entities share patterns. It is optional for straightforward UI or one-off gameplay objects.

Strong candidates

  • Many actors with shared movement, render or lifetime data.
  • Component-driven gameplay states and entity filtering.
  • World3DEXT scenes, which already use ECS as their scene organisation layer.

Keep simple objects simple

  • Single temporary value objects with no shared processing.
  • A screen-level controller whose state has no entity dimension.
  • UI behaviour that is clearer as direct Screen code.
