10 · WORLD3DEXT

A 3D scene layer that stays at home in cna-extended.

World3DEXT is a non-upstream 3D extension. It builds a scene system from the existing Screen and ECS modules instead of introducing a separate, competing scene-management abstraction.

THE ENTRY POINT

World3DScreenEXT turns one screen into one 3D scene.

The class owns a Camera3DEXT and an ECS World, while continuing to use Screen’s normal initialize, update and draw lifecycle.

Camera3DEXT

A dedicated 3D camera rather than a forced 2D generic-camera adaptation. It provides the view/projection/frustum information needed by 3D render systems.

ConfigureWorldEXT

Override this hook to transfer systems into the WorldBuilder. It runs once from Initialize(), before the World exists.

Derived Initialize()

If a derived screen overrides it, call World3DScreenEXT::Initialize() first; only then is GetWorld3DEXT() valid for entity creation.

complete system-registration shape
class MyWorldScreen final : public World3DScreenEXT {
public:
  explicit MyWorldScreen(GraphicsDevice& device) : device_(device) {}

protected:
  void ConfigureWorldEXT(ECS::WorldBuilder& builder) override {
    builder.AddSystem(std::make_unique<TransformHierarchySystemEXT>());
    builder.AddSystem(std::make_unique<RenderSystem3DEXT>(
      device_, GetCamera3DEXT()));
  }

private:
  GraphicsDevice& device_;
};

SCENE FEATURES

World3DEXT covers the main 3D building blocks.

Every area is designed to connect through ECS, but the helper classes remain usable where a direct integration is appropriate.

01

Transform hierarchy

Transform3ComponentEXT bridges an entity to transform data; TransformHierarchySystemEXT updates parent/child relationships in ECS terms.

02

Models and culling

ModelComponentEXT plus RenderSystem3DEXT renders Model data and skips entities outside the camera frustum.

03

Skinned animation

SkinnedModelComponentEXT and AnimationSystem3DEXT reuse cna’s SkinnedModelEXT animation/rendering path.

04

3D collision

Shapes, actors, events, pairs, layers and broadphase implementations form the 3D counterpart to the 2D collision world.

05

Visual helpers

Cube meshes, billboards, animated billboards, world-space text and line-based debug drawing accelerate prototyping and tools.

06

Particles and voxels

Plugin-based 3D particles and sparse voxel tilemaps round out the scene feature set.

MODELS, SKINNING & VISIBILITY

Make a model entity, then let the renderer filter it.

World3DEXT deliberately keeps gameplay components separate from actual draw code. The render system uses transforms and bounds when deciding what reaches the device.

Static model path

  • Attach ModelComponentEXT to an entity.
  • Optionally attach a transform component for a non-identity world matrix.
  • Set suitable local-space model bounds; the renderer transforms and tests them against the camera frustum.
  • RenderSystem3DEXT delegates the normal model path through cna’s model drawing APIs.

Skinned model path

  • Attach SkinnedModelComponentEXT and configure the cna SkinnedModelEXT data.
  • Add AnimationSystem3DEXT to advance the selected animation clip.
  • Use the same renderer; it follows the established cna skinned-effect drawing recipe.
  • Keep the GraphicsDevice and Camera3DEXT references alive for the renderer’s entire lifetime.
i

Why the GraphicsDevice is a renderer constructor argument: ordinary models have their normal cna draw route, while skinned mesh parts require the device for their explicit draw sequence. This is why RenderSystem3DEXT holds both device and camera references.

3D COLLISION

Start with spatial hashing; opt into the octree when it fits.

CollisionWorld3DEXT mirrors the 2D world’s layered actor/query design while using 3D bounding volumes and broadphase implementations.

Default behaviour

A default-constructed 3D collision world creates a default layer backed by SpatialHash3DEXT(16.0f), so a simple Insert(actor) flow works without initial layer construction.

Layers and queries

Named Layer3DEXT and LayerPair3DEXT filter allowed collisions. Query candidates, concrete collision events and collision pairs mirror the 2D mental model.

SpatialHash3DEXT

Use the bucketed default for many normal moving actors and predictable local neighbourhood queries.

Octree3DEXT

Use the recursive-subdivision opt-in broadphase when your world’s spatial distribution calls for an octree rather than hash cells.

BILLBOARDS, DEBUG & 3D PARTICLES

Build readable worlds before you build final art.

The visual helper types are especially useful during scene construction, because they surface spatial problems without requiring a finished model pipeline.

Cube mesh

CubeMeshComponentEXT and its render system provide textured or coloured cubic geometry — useful for prototypes, voxel rendering and scene markers.

Billboards and text

Billboard components/render systems orient sprites to the camera. Animated billboards and Text3DEXT extend the pattern for effects and world labels.

Debug draw

DebugDrawComponentEXT and DebugDrawSystemEXT use line batches, including sphere-wireframe support, to expose spatial bounds and helpers.

Effect and emitter

ParticleEffect3DEXT, ParticleEmitter3DEXT, update and render systems connect 3D particles to ECS.

Full plugin architecture

3D particles have 8 profiles, 11 modifiers and 6 interpolators rather than a single hard-coded update recipe.

Shared rendering

Particle drawing reuses the extracted billboard draw path, so particle appearance and standalone billboard behaviour stay aligned.

VOXEL TILEMAPS

Use sparse 3D grid data for tiles, collisions and batching.

The 3D map system is not a 3D interpretation of a Tiled/LDtk/Ogmo export. It is a purpose-defined voxel grid with an explicit JSON schema.

Tilemap3DEXT

A sparse tile grid: ID 0 means empty. Tile sizes are world-space Vector3 values, so cells do not have to be cubes.

Factory inputs

Tilemap3DFactoryEXT::BuildFromArrayEXT accepts flat X-fastest/Y-then-Z tile IDs. JSON file/stream methods parse the project-defined Tilemap3DFileContent schema and delegate to the same construction logic.

Rendering choices

TilemapRenderer3DEXT draws visible tiles through cube rendering. TilemapChunkRenderer3DEXT batches visible faces by (chunk, texture) to reduce draw calls.

Collision bridge

TilemapCollisionActor3DEXT and RegisterTilemapCollisionActorsEXT register populated tiles into a 3D collision world in bulk.

construct a small voxel map from array data
std::vector<int> ids = {
  1, 1, 1, 1,
  1, 0, 0, 1,
  1, 1, 1, 1
};

Tilemap3DEXT map = Tilemap3DFactoryEXT::BuildFromArrayEXT(
  ids, 4, 1, 3, Vector3(2.0f, 0.5f, 2.0f));

// 0 is empty; other IDs are resolved through a TilemapTileset3DEXT.
!

Do not expect a generic editor import: the voxel JSON format is project-defined because Tiled, LDtk and Ogmo model 2D maps. Use their 2D loaders for their intended data, and use the 3D factory/schema for voxel worlds.

REFERENCE IMPLEMENTATION

The world3d demo is an end-to-end integration test you can read.

examples/world3d_demo combines transform hierarchy, frustum-culling, a skinned character, particles and a voxel floor, then reads a rendered frame back for validation.

  • Registers transform, animation, particle update and rendering systems in one World3DScreenEXT subclass.
  • Uses cube, billboard and model paths in the same scene.
  • Demonstrates cna’s render target/readback workflow, including the need for a real depth format for depth-tested 3D rendering.
  • Serves as the best reference for system ordering and component construction in a complete 3D program.
